Real-Time Object Detection on Raspberry Pi

01

Project context

This project explored whether a low-cost Raspberry Pi 3 could run deep-learning-based object detection while also supporting a continuously displayed camera stream. The target use case was small indoor monitoring, where objects move relatively slowly and the system can operate with a fixed camera.

The prototype used a Logitech C615 USB camera for image acquisition, a MobileNet-based detector through OpenCV for recognition, and a laptop connected over LAN for remote monitoring.

Important performance distinction: the camera/display path operated at about 29 FPS, but neural object detection itself was reported at only about 0.9–1 FPS on the Raspberry Pi 3. The project therefore demonstrated live video monitoring with periodic embedded inference rather than 20+ FPS neural detection.

The detector was configured for 20 predefined object categories and returned a bounding box, class label, and confidence for recognized objects.

02

Requirements and Constraints

The original design specification combined cost, recognition quality, continuous operation, remote monitoring, and real-time behavior. Some values were aspirational requirements rather than achieved prototype results, so I separate them from the measured results later in this case study.

Area Original requirement / design target
Cost Keep the device below approximately 4 million VND.
Recognition Target approximately 90% or higher recognition accuracy.
Video Maintain a high camera/display frame rate, with the specification targeting more than 20 FPS.
Operation Continuous monitoring, remote access, and a fixed camera installation.
Environment Indoor use, sufficient lighting, and relatively slow-moving objects.

The presentation also listed automatic reset and backup power as desired functional requirements. These were part of the system requirements, but the final slides do not provide evidence that they were implemented in the prototype.

03

Hardware and Software Stack

Component Purpose
Raspberry Pi 3 Model B Runs Raspbian, captures frames, performs object detection, and manages the concurrent display/inference paths.
Logitech C615 USB camera used to capture approximately 640 × 480 video at around 29–30 FPS.
MobileNet-SSD + OpenCV Lightweight deep-learning detector selected for operation on resource-constrained hardware.
Laptop + Remote Desktop Receives the Raspberry Pi desktop over LAN and displays the live stream and detection results.

The reported hardware cost was approximately 3.25 million VND: about 2 million VND for the camera, 1.2 million VND for the Raspberry Pi 3, and roughly 50,000 VND for the 5 V / 2.5 A power supply. This kept the prototype below the initial 4-million-VND budget target.

04

System Architecture

Camera-to-display path

The system was organized around three hardware blocks: image acquisition, embedded processing, and remote display. The camera sent frames to the Raspberry Pi through USB. The Pi handled both the live-video path and the recognition path, while the laptop displayed the result through a LAN Remote Desktop connection.

Concurrent processing on the Raspberry Pi

A key design decision was to avoid making the slow object-detection stage block the live video display. The Raspberry Pi used multithreading so that frame acquisition/display and object recognition could proceed as concurrent paths.

This separation was necessary because the camera produced roughly 29–30 frames each second while the detector processed only about one frame each second. Keeping the two paths separate allowed the displayed stream to remain responsive even when inference was much slower.

05

Software Pipeline

The software flow in the presentation begins by loading the model and system configuration, resizing frames, initializing the application classes and queue, and starting the video source. The main loop then captures frames and feeds the two concurrent paths.

06

Results

The final prototype successfully connected the USB camera to the Raspberry Pi, exposed the Pi through Remote Desktop, and ran the MobileNet-SSD detector on live camera input.

Camera / display ~29 FPS
Detection ~0.9–1 FPS
Reported accuracy ~90%
Remote delay ~0.2 s

The important engineering result was not that every frame could be processed by the neural network. Instead, the architecture kept the live video path responsive while periodically updating the object-detection result in parallel.

07

Limitations and Next Steps

  • Inference speed was the main bottleneck. The Raspberry Pi 3 processed only about one detection frame per second, so the prototype was better suited to slow indoor scenes than fast-moving surveillance targets.
  • The original performance requirements were more ambitious than the measured prototype. The presentation listed targets above 20 FPS and very low communication latency, but the reported implementation achieved approximately 0.9–1 FPS detection and about 0.2 s remote-display delay.
  • Remote Desktop was practical for demonstration, not an optimized video-delivery architecture. A dedicated streaming/output path would provide better control over latency and bandwidth.
  • Reliability features remained requirements rather than demonstrated results. The slides proposed automatic reset and backup power, but do not show their implementation.
  • A modern revision would focus on model/runtime acceleration. Quantization, a lighter inference runtime, hardware acceleration, and bounded frame queues would be natural next steps while preserving the same decoupled display/inference architecture.
