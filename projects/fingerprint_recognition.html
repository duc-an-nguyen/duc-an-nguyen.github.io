01

Project context

This project focused on building the complete fingerprint-recognition path rather than treating the fingerprint sensor as a black-box identification module. The goal was to understand and implement the major processing stages ourselves, from raw grayscale fingerprint data to a final identity match.

I first developed the algorithm in MATLAB so that each processing stage could be inspected and compared visually. I then implemented the same recognition logic in C/C++ and simplified computationally expensive parts to move the design closer to the constraints of embedded hardware.

The input data came from an FPC-AM3 fingerprint acquisition kit. Raw 8-bit grayscale images were transferred to the computer through UART, with an original size of 200 × 152 pixels. The recognition pipeline normalized the working image to 192 × 144 pixels before further processing.

Low-level implementation highlight: the C processing path did not use OpenCV or another computer-vision framework. I worked directly with the raw 8-bit image buffer and implemented the required processing stages as C functions. Standard C file operations were used to read the headerless sensor data, while MFC was used only for the desktop interface and visualization. The MATLAB reference did use a published open-source STFT enhancement implementation as a starting point, so it would be inaccurate to describe every MATLAB component as written entirely from scratch.

Deployment scope: the completed implementation was evaluated in MATLAB and in a C/C++ desktop prototype. The work was designed as a step toward embedded deployment, but the available project results do not demonstrate a completed microcontroller implementation.

02

Recognition Strategy

The recognition method was based on minutiae: local ridge structures that remain useful even when only part of a fingerprint is visible. The two main feature types used by the pipeline were ridge endings and ridge bifurcations.

Raw fingerprint images can contain weak contrast, broken ridges, background regions, partial contact, and noisy ridge structures. For this reason, matching could not be applied directly to the sensor image. The pipeline first enhanced the ridge pattern, isolated the valid fingerprint region, converted it to a clean one-pixel-wide ridge representation, and then extracted stable minutiae for comparison.

Stage Purpose
Normalization and histogram equalization Standardize the working image size and improve ridge/valley contrast.
STFT enhancement Estimate local ridge structure and strengthen fingerprint patterns in the frequency domain.
Segmentation Separate useful fingerprint regions from background areas.
Otsu binarization Convert local grayscale ridge patterns into a binary representation.
Thinning Reduce each ridge to approximately one-pixel width for structural analysis.
Minutiae extraction and cleanup Detect ridge endings/bifurcations and remove likely false features.
Alignment and matching Compensate for translation/rotation and calculate the similarity between fingerprint templates.
03

End-to-End Pipeline

The final workflow connected image enhancement, ridge processing, feature extraction, and identification into one sequential recognition pipeline.

04

Image Processing and Feature Extraction

STFT Enhancement

The most computationally intensive preprocessing stage used Short-Time Fourier Transform (STFT) analysis to strengthen the local ridge structure. The image was processed in overlapping windows so that ridge orientation, local frequency, and energy could be estimated region by region rather than assuming the entire fingerprint had one direction or spacing.

This local frequency-domain description was then used to reconstruct a clearer fingerprint pattern. The improvement was especially useful where the raw image contained weak contrast or interrupted ridge detail.

Segmentation, Binarization, and Thinning

After enhancement, the pipeline isolated the valid fingerprint region and applied automatic Otsu thresholding to convert the grayscale ridges into a binary image. The binarization step was performed locally in blocks so that the threshold could follow spatial changes across the fingerprint.

The binary ridges were then thinned iteratively until the structure was approximately one pixel wide. This skeleton representation made it much easier to reason about ridge topology and detect endings or bifurcations.

Minutiae Extraction and Cleanup

Ridge endings and ridge bifurcations were detected from the thinned image. A raw detector can create false minutiae around small artifacts, broken ridges, and nearby structures, so I added a cleanup stage that examined the relationships between neighboring features and the corresponding ridge information before saving the template.

05

Fingerprint Matching

The matching stage had to handle the fact that two captures of the same finger are rarely placed at exactly the same position or angle. The implementation therefore separated matching into two main steps: alignment followed by minutiae comparison.

Candidate minutiae from the input and template were tested as possible corresponding anchor points. Their associated ridge information was used to reject unlikely anchor pairs and estimate the required rotation. After selecting an anchor pair, both minutiae sets were represented relative to that origin, allowing the input fingerprint to be rotated and compared in a common coordinate system.

Aligned minutiae were considered corresponding when their positions and directions were sufficiently close. The number of valid correspondences was converted into a similarity score, and the database entry with the highest score was selected as the recognition candidate.

For evaluation, each fingerprint was compared against the remaining entries in the database. With 255 samples, this meant up to 254 template comparisons for one query, which later became one of the main runtime bottlenecks.

06

Low-Level C/C++ Implementation and Optimization

MATLAB was useful for validating the processing sequence and inspecting intermediate images, but the harder engineering task was reproducing that behavior in a lower-level implementation with much less help from high-level image-processing tools.

Direct image processing in C — no OpenCV

The C implementation did not rely on OpenCV for image loading or processing. The fingerprint sensor produced a headerless .raw image containing a 200 × 152 matrix of 8-bit grayscale values. I read that data directly with standard C file operations such as fopen() and fread(), stored the pixels in image arrays, cropped the working region to 192 × 144, and passed those arrays through the processing functions.

This meant that the practical C pipeline had to explicitly handle operations that a modern vision library normally hides: raw image I/O, pixel indexing, histogram processing, segmentation, thresholding, thinning, minutiae detection, false-minutiae removal, template serialization, and matching. MFC was used for the GUI, but even displaying the raw fingerprint required manually converting the pixel data for StretchDIBits() because MFC did not natively understand the sensor's raw image format.

Important distinction: the MATLAB reference was not completely library-free. The project used a published open-source MATLAB implementation for the STFT fingerprint-enhancement stage as a reference component. The engineering contribution was to understand the complete processing chain, adapt it, implement the remaining recognition stages, and reproduce the practical pipeline in C/C++ rather than calling OpenCV-style image-processing functions.

Build and execution environment

The documented C/C++ application was built with Visual Studio 2013. The GUI was written with MFC in C++, and the image-processing and recognition routines written in C were integrated into that application. The project report does not document a Makefile or GCC-based build, so I have not added a Makefile workflow to this case study without source evidence.

Making the MATLAB pipeline practical in C

A direct translation was still too expensive, especially in the STFT stage. I therefore simplified the implementation while preserving the recognition behavior:

  • Removed non-essential filtering operations that added computation without enough benefit for the selected input conditions.
  • Replaced repeated sin() and cos() evaluations with lookup tables. The report measured more than a 7× improvement for these calculations, reducing the relevant STFT computation from roughly 7 seconds to under 1 second.
  • Computed only the information actually required downstream. Where a full local frequency map was not necessary, the C implementation reduced the amount of frequency information that had to be retained and processed.
  • Restricted severely damaged inputs rather than spending large amounts of processing time trying to reconstruct fingerprints that still produced unreliable minutiae.
  • Validated the rewrite against MATLAB. In the reported 30-sample comparison, both implementations returned the same best-matching fingerprint and the same similarity percentage for every tested sample.

Template storage and 1:N recognition

The MATLAB prototype stored fingerprint templates as separate data files. In the C version, template handling was redesigned so that minutiae and their associated ridge information could be read efficiently during recognition. The recognition stage then performed a 1:N search, comparing one input fingerprint with the stored templates and selecting the highest similarity score.

This exposed a second major performance problem: with 255 samples, one query could require up to 254 individual comparisons. The implementation worked at this scale, but exhaustive matching became an obvious scaling limit for a database containing thousands of fingerprints.

Engineering Challenges That Mattered

Challenge Why it mattered Engineering response
Working without an image-processing framework in C Raw sensor bytes could not simply be passed to an OpenCV-style image API. Handled raw 8-bit buffers directly, implemented the processing stages as C functions, and built a custom display path in MFC.
Expensive STFT enhancement Frequency-domain enhancement dominated runtime and blocked an embedded-oriented implementation. Removed unnecessary operations and replaced repeated trigonometric functions with lookup-table approximations.
False minutiae after thinning Noise, broken ridges, and skeleton artifacts can look like valid ridge endings or bifurcations and corrupt matching. Added explicit false-minutiae cleanup and used associated ridge information rather than accepting every detected point.
Translation, rotation, and partial fingerprints The same finger can appear at a different location and angle, with part of the ridge pattern outside the sensor area. Tested candidate minutiae anchors, estimated rotation, transformed features into a common polar frame, and matched using position and direction tolerances.
Preserving MATLAB behavior after a C rewrite Optimization is not useful if it silently changes the recognition result. Compared both implementations directly; all 30 sampled cases produced the same best match and similarity score.
Scaling exhaustive matching Recognition time grows with the number of stored templates. Profiled 1:N matching as a separate bottleneck and identified classification/indexing as the next step for larger databases.
07

Results and Bottlenecks

The evaluation used 255 fingerprint samples from 27 different fingers. Each finger was captured multiple times, and the set deliberately included both good and poor-quality acquisitions so that the behavior under difficult inputs could be observed rather than hidden.

Dataset 255 samples
Finger identities 27 fingers
Good-quality recognition 67.96%
Average C runtime 4.373 s

MATLAB and C consistency

Thirty randomly selected samples were evaluated with both implementations. For every sample in that comparison, MATLAB and C returned the same highest-matching fingerprint ID and the same similarity percentage. This gave a useful implementation check: the lower-level rewrite preserved the recognition behavior of the reference pipeline.

Effect of fingerprint quality

Input group Samples Successful recognitions Recognition rate
Good-quality captures 181 123 67.96%
Poor-quality captures 74 8 10.81%

This difference was significant. Roughly 29% of the evaluation set consisted of poor-quality samples, including partial captures and heavily damaged ridge patterns. The results therefore showed both the capability of the pipeline and its sensitivity to acquisition quality.

Where the runtime was spent

Processing group Average time Share of total runtime
STFT enhancement 2.739 s 62.62%
1:N matching 1.497 s 34.22%
Other processing stages 0.137 s 3.13%
Total recognition pipeline 4.373 s ≈100%

The profiling result was useful because it made the next optimization priorities clear: most of the runtime was concentrated in STFT enhancement and exhaustive template matching, not in binarization, thinning, or the remaining lightweight image-processing stages.

08

Limitations and Next Steps

  • STFT enhancement remained the largest computational bottleneck. The implementation used a direct Fourier-transform approach in this stage; replacing it with a more efficient FFT-based implementation would be a clear optimization path.
  • Exhaustive 1:N matching scaled poorly. Comparing one query against every stored template was acceptable for 255 samples but would become increasingly expensive for databases containing thousands of fingerprints. A classification or indexing stage could reduce the search space before detailed matching.
  • Recognition was strongly dependent on acquisition quality. Poor or severely damaged ridge patterns produced much lower recognition rates. The report also notes difficult cases around noisy/corrupted samples and captures containing complex core regions, where reliable minutiae extraction becomes harder. Stronger quality assessment and more robust feature handling would be needed.
  • The C implementation was not yet a completed microcontroller deployment. Further reduction of memory use and execution time would be required before moving the full pipeline to a constrained embedded target.

The strongest outcome of the project was the complete engineering path: I could trace a raw fingerprint through enhancement, segmentation, ridge processing, minutiae extraction, alignment, and matching; verify the C implementation against MATLAB; and profile exactly which stages prevented the algorithm from being immediately moved to smaller hardware.
